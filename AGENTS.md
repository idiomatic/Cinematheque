# Cinematheque

Local-first video libraries. Players on Apple devices, macOS, Linux, and Windows browse shared libraries and play each video from any repository that holds it. There is no central server: each library's titles, metadata, and user data replicate among peers, so every peer works offline and catches up when it reconnects.

This file specifies what's built. How operations are written, merged, and synced, and the keys and fields the library writes, are in [ARCHITECTURE.md](ARCHITECTURE.md); plans and open questions are in [DEVELOPMENT.md](DEVELOPMENT.md); the measurements behind the design are in [experiments](experiments/README.md); outside specifications are indexed in [docs/specifications](docs/specifications/README.md).

## Components

* [core](core/README.md): the Zig library, and a static library with a C interface ([cinematheque.h](core/include/cinematheque.h), a Swift module by its [module map](core/include/module.modulemap)) whose results are JSON (see [Core interface](#core-interface)).
* [peer](peer/README.md): the command-line desktop peer, `cinematheque`, for macOS and Linux.
* [apple](apple/README.md): the Apple players, in SwiftUI: one multiplatform app, `com.rbrian.cinematheque`, for macOS 15 or later and tvOS 18 or later (see [Apple players](#apple-players)).
* [experiments](experiments/README.md): the prototypes the components grew from, kept for reference.

## Core interface

* **Threads:** its functions belong to one thread but for long ones (crawling, syncing, describing), each on a connection of its own; only one connection writes as the device at a time, and the main one catches up (`Replica.refresh`) before acting. Strings passed in are copied if kept.
* **Long operations** commit as they go; `cq_data_version` changes when they have, `cq_progress` tells how far one has come (its phase, and steps done of how many), and `cq_prioritize` names titles (e.g., those on screen) for a crawl to describe first.
* **Serving and syncing:** `cq_serve` serves the library (and folders, each at a path of its own) on a task of its own until `cq_stop_serving` or `cq_close`; `cq_served` tells of the last sync it served (to which device, how many operations), and `cq_received` of the last push it took (from which device, how many operations won); `cq_sync`'s results name each peer as it advertised itself, and say how many operations were pushed to it.
* **Pairing:** `cq_pair_offer`, `cq_pair_check`, and `cq_pair_stop` offer a new device to pair, to link or to join, and `cq_pair` pairs one, returning its user's key and its own; `cq_name` names another device, as one just paired.
* **People and devices:** `cq_status` tells whether this device is linked to another's user. `cq_set_name`, `cq_devices`, `cq_peers` (found nearby, with names, and added), and `cq_peer` (adding one by address) let apps show people and devices by name. `cq_remove_playhead` removes one of this user's playheads, and `cq_remove_device` another device.
* **Downloads:** `cq_downloads_configure` sets where a device keeps downloads and the URL it serves them at, `cq_download` and `cq_keep` say what to keep, `cq_pin` keeps a download however it's watched, `cq_download_remove` deletes, `cq_downloads` tells all of it (what's held, wanted, kept, pinned, and watched since downloaded, free space, and how far reconciling has come), and `cq_reconcile` (long) fetches and deletes to match; while one runs, another asks it to run again and returns.

## Peers

* **Players:** every client, each able to sync and crawl as well as play.
* **Refreshing:** every peer syncs with peers first, then crawls: the catalog other peers have crawled and described arrives first, so the crawl finds little to do (a device's first crawl after syncing adds and describes nothing unchanged).
* **Repositories:** anything that serves videos over HTTP.
* **Static servers:** repositories running no Cinematheque code, such as a consumer-grade NAS or a web server (Caddy, nginx, Apache).
* **Desktop peers:** macOS, Linux, and Windows players. They are repositories too, serving their local and downloaded videos, and differ from static servers only in what they hold and how long they stay online.

## Identity and membership

* **Home:** the peer's own directory ("home," so it isn't taken for media): `~/Library/Application Support/Cinematheque` on macOS, `$XDG_DATA_HOME/cinematheque` (`~/.local/share/cinematheque`) elsewhere, or another by `--home` or `CINEMATHEQUE_HOME`, which the C interface, and so the app, honors too. It holds `identity` (the device's random seed), `user` (the user's seed, if linked), `library` (the founder's user key), and `replica.db`.
* **Keys:** a device's keys derive from its seed, and its user's from the user's seed, which the user's devices share; a device not linked derives its user's seed from its own. Linking a device means giving it the user's seed, which is a secret, and is done only by pairing, so the seed is never shown.
* **Pairing:** a new device, before it has a library, shows a 6-digit code and offers to pair, to link (to be another of a member's user's devices) or to join (as a new member), serving `/pair` and advertising `pair` (`link` or `join`) by DNS-SD. A member's device, given the code, sends it the founder's key, and if linking, the user's seed, sealed with a key both derive by CPace (ristretto255, SHA-512) from the code and the offer's kind, so an eavesdropper learns nothing, each attempt tests one guess, and the kind can't be changed on the way. The new device answers with its user's key and its own, sealed the same way: a joining one's user is added as a member, and the member's device names the new device, as it advertised itself, under its user (the member's, if linking), so it's listed among that user's devices at once, until it names itself. It stops after 3 wrong codes, until it offers again with a new one.
* **Certificates:** a device's first write is its certificate, its user's signature over the library and the device key. A device's private stream has a certificate of its own. Before writing, once a connection, a device checks its own certificates (its stream's, and its private stream's, which travels on its stream) and writes any missing or invalid one afresh, at the current time so it wins; the apps, on opening the library, rewrite one they hold that doesn't verify, without waiting to write (but never write a missing one first, since a device whose replica was lost must sync first): a device's own writes pass without one, so only other devices would notice, by refusing its whole stream (as one an older build certified wrongly).
* **Library:** its ID derives from its founder's user key. Members add users to a set; any member may remove another, except the current founder.
* **Handover:** the founder may hand the library over to a member, staying or leaving. Handovers are a numbered chain, each valid only if written by the previous generation's founder, so peers agree in any order.
* **Removal:** any member may remove a device, without its user, or a member, with every device of theirs it knows. Each device's streams (its own and its private one) are cut off where the remover had seen them (`revoked`, a field per stream): writes through there stand, later ones are refused, and peers serve it no more; a removed member's device the remover didn't know isn't admitted. A peer that took later writes before hearing of the removal drops them, notes their fields, and repairs them from a peer that refused them, fetching just those fields' winners with one shared proof per batch; a write only it held, which lost to a refused one, is lost. A removed device still holds its user's seed, so it could pair again as a new device; keeping it out for good would take a new user seed. A removed device is told so when it next syncs: the peer refusing it signs a refusal (`removed`) over the library, the device, and its request's time, which the device believes only if a member certified the signer and it doesn't know the signer removed; it then forgets the library and its identity (`cq_leave`; on tvOS, the Keychain's seeds too) and returns to setup, saying why, to pair again as a new device.

## Replication

* **Operations:** each writes one field of one key. Fields merge last-writer-wins by hybrid logical clock, ties broken by device key; set elements merge by causal length.
* **Batches:** a device signs each batch of up to 1,024 consecutive writes (a transaction's) once, with Ed25519, over a BLAKE3 Merkle tree of their encodings, so any operation, or set of them, is verifiable by proof.
* **Storage:** SQLite holds each field's winning operation (as columns, from which its encoding is rebuilt), interned device keys, signed batches, a version vector of each device's highest sequence number covered, fields awaiting repair, and state of the peer's own (`local`, e.g., crawl snapshots). It runs in WAL mode, and connections wait up to 10 seconds for one another's writes, since a peer's `serve` and `refresh` share its replica.
* **Sync,** both ways, started by either side: a device POSTs to `/sync` a request signed by its device, with its certificate, the time, and its version vector. The peer answers members only, within ten minutes of its own clock, with frames: per device, its winning operations above the vector, grouped by batch, each batch with its signature and the leaves of operations not sent; then its vector, which the device adopts; and its own device key and certificate, in headers. The device then pushes what the peer lacks: a second POST to `/sync` (its own content type) of a signed request and the frames above the peer's vector, leaving out private streams not the peer's user's, which the peer applies as it would a response. So a device that can reach a peer, though the peer can't reach it (behind a NAT), syncs both ways. Frames are gzipped; a peer too old to take pushes refuses one, and is only pulled from.
* **Own private stream:** a device takes its own private stream's batches as its user's even before the certificate arrives, so a device whose replica was lost (as tvOS may purge one) gets its playheads back from its user's other devices.
* **Admission:** a receiver applies a batch only if its device's certificate names a member, else holds it until the end of the response, then rejects it without claiming it in its vector. It refuses operations past a removed device's cutoff, handovers not from the previous founder, and private data not from its user's private stream.
* **Private data:** a user's playheads (`p/<user>/...`) are written on each device's private stream, with its own key and numbering. Peers send private streams only to their users' devices, and leave them out of the vectors they send others, so private data travels only directly between a user's devices.

## Library

* **Keys:** `t/<m|s>/<normalized title>/<year or ->` for a title; below it `/v/<edition or ->` for a movie's version (its `edition` field naming it as written) or `/e/s03e17` for an episode (then `/v/<edition>` for an episode's version; `/e/s00-<normalized title>` for a special without a number, its `title` field naming it), `/p/<n>` for a part, and `/r/<rendition>`, whose `held:<repository>` field records the file's path, size, and modification time, empty when no longer held. A title's key derives from its parsed identity, so peers crawling independently agree.
* **Naming:** the parser reads Plex, Jellyfin, and Kodi conventions and download names: ID tags, years (the last year ends a title), editions, parts (after the year), extras, `S01E02`, `1x02`, air dates, season folders, and Kodi's compact codes (`Show 317 Title`) right after the series' title from the enclosing folder. Dots between digits are a title's own (`11.22.63`); a name of numbers alone without a year (e.g., a camera's) goes to review. A numberless file beside a series' episodes whose name extends the series' (`Babylon 5 The Gathering`), or in a `Specials` folder, is a special (season 0).
* **Renditions:** a file's rendition is its repository's, if named; else its name's technical tokens, canonically (resolution, source, codec, dynamic range, e.g., `2160p remux hevc hdr`); else unknown (`-`). Two files of one rendition in one repository are numbered (`~2`) as duplicates.
* **Review:** among titles some repository holds, close matches (a year off by one, missing, or with transposed digits; the same year, the same digits, and a spelling within two edits; or only diacritics differ) and duplicates. An alias (`aliases`) records that one title key is another's; it replicates, and an empty one undoes it.
* **Playheads:** per user and item (version, episode, or part), above renditions: position and duration in milliseconds, and watched, set on reaching the last 5% or by hand. A position in the first 10 seconds isn't kept: recording one empties the position and duration (not the watched mark), so stopping at the start sticks. Removing a playhead empties all three.
* **Covers and metadata:** after each crawl, one file per movie and per season, across every repository, describes it, unless the file that last did is unchanged; else the best (a sidecar, then an MP4, then another file; a movie's standard version before its editions). Describing runs after crawling, so titles show before covers, with 16 workers, prioritized titles first, committing every 24 jobs or 750 ms. A network failure is retried next crawl; a file that isn't a readable MP4 records an empty cover, so it isn't reread until it changes. The cover comes from a sidecar image by Plex, Jellyfin, and Kodi convention (`poster.jpg`, `folder.jpg`, `<movie>-poster.jpg`, `season01-poster.jpg`, a season folder's `poster.jpg`), else an MP4's, read by range requests that walk atom headers to `moov` and read `udta` whole (about 8 requests). The cover is recorded as a byte range of the file (`art`, or `art:s01`... for seasons, on the title's key), so players fetch it with one range request; images don't replicate. Each cover's placeholder replicates: `thumb` (or `thumb:s01`...), a ThumbHash in base64 of its JPEG's DC coefficients (an eighth-size image, decoded without a full decode), or `-` for another format; players render it with `cq_thumbhash`. A cover described without one gets one from a single range request. MP4 metadata fills a title's `description`, `genre`, `released`, and `network`, and an item's `title` (an episode's), `description`, and `duration`; other episodes are described on demand.
* **Tiles:** for browsing, a movie or a season (a season without a cover takes its series'), with this user's progress: watched if every item is, else the share of its running time played (watched items whole, so one stopped in its last 5% counts in full, and items partway to their positions; an item of unknown length takes the average of those known), with the milliseconds elapsed and the runtime; and whether any item has a playhead (begun), which puts a season with an episode partway on Home and Played.
* **Watchlist:** per user, private like playheads (`p/<user>/watchlist`, a field per movie's title key, or per season, `<title key>#<season>`, each season listed on its own).
* **Names:** users' and devices' (`n/<key>`'s `name`, and a device's `user`, its user's key), set by any member, shown in place of keys.
* **Facets:** titles held by some repository, counted by kind, decade, and rendition.

## Repositories

* **Settings:** a repository is a URL (percent-encoded as typed), with an optional rendition name and a prefix of names to skip (default `,`), changeable later (applied at the next crawl). Its ID is a hash of the URL. Removing it clears its settings and copies for every peer, and the remover's crawl snapshot.
* **A device's downloads:** a repository of its own, `managed` (a replicated field), which no peer crawls: each file fetched is recorded as its holding on the very rendition it came from, so peers see it and play from it. What a device keeps is its own (`local`): items wanted (a title or season wanted is its items as of then, each in the rendition the player's picker shows), and per series, the next N episodes after where its user is (from the latest in progress, else the first unwatched, specials aside). Files go under their paths in the repository they came from, into `<path>.part` resumed by a range request, never written past their size, and only within the folder. A download watched since it was fetched (its watched mark's clock past the fetch) is done with, unless pinned: deleted, wanted no longer, only once another repository holds it alike (its rendition and size, not absent), at once if the device says so, else only as its space is needed, oldest fetched first; the only copy, never. Reconciling also forgets holdings whose files are gone (deleted by hand, or the folder changed), and never leaves less than 20 GB free.
* **Listings:** a crawl reads an `INDEX` if there is one (a path per line, as `find . -type f ! -name INDEX > INDEX` writes them, optionally followed by tab-separated size and modification time; a directory's ending in `/`, as Cinematheque's server lists them, so an empty one shows it's still there), else JSON listings (Caddy's or nginx's), else HTML, reading only links' targets.
* **Crawls:** breadth-first with concurrent workers (16 by default), reusing a previous crawl's listing of any directory with only files whose modification time hasn't changed, then bringing the repository's holdings in line with what was found. A crawl that fails anywhere changes nothing. A directory that held files and is still listed but holds none (an unplugged drive's mount point, or a NAS's) is absent: one field on the repository, `absent:<directory>` (relative to it, empty for the whole of it), noting when, its holdings kept, rather than an operation per file; the topmost of an absent subtree only. A crawl clears it once the directory lists files again, or is gone from its parent's listing (deleted, its holdings going as deleted files' do), or a year on, as if deleted; or a person forgets it, as if deleted. Players show a title whose copies are all absent dimmed, and try absent copies last.
* **Serving:** a peer listens on the port given, else on 8008 or, if that's taken, any free port, and advertises the port it got. It binds with `SO_REUSEADDR` alone, never `SO_REUSEPORT`, so no two processes share a port. It answers `/sync`, and optionally serves media directories, each at the root (the command-line peer's one) or at a path of its own (the apps'): files with single byte ranges, `If-Range`, and `mtime-size` ETags; listings as JSON (Caddy's form, on `Accept: application/json`) or HTML; and, at the root, an `INDEX` with sizes and times, and directories (built at start, and again on a request once it's a minute old, so drives plugged in or unplugged show; the apps' changing folders have none, and crawls read their live listings; each of the apps' folders is opened afresh for each request, and one that isn't there, as a share unmounted, lists empty at its root, so a crawl finds it absent rather than failing).
* **Discovery:** peers advertise `_cinematheque._tcp` by DNS-SD (Bonjour on Apple platforms, Avahi's compatibility library on Linux), named for the device's key (`cinematheque-` and its first 8 hex digits), so a user's devices are told apart and a peer skips only itself, with the library's ID, the sync path, the user's key, and the device's and user's names in the TXT record, so a device of the library whose user isn't a member yet can be shown, by name, to add; a new device offering to pair advertises `pair` (`link` or `join`), the pairing path, and its name instead.

## Peer

* **Commands:** [usage.txt](peer/src/usage.txt) lists them, and is their help. Devices join and link only by pairing; an offer prints its code and the port it listens on, for a device that can't find it nearby (`pair CODE URL`). State commands are `NOUN VERB`, with verbs `list`, `show`, `add`, `set`, and `remove` where they apply, over nouns `user`, `library`, `member`, `device`, `repo`, `title`, `alias`, `playhead`, `peer`, and `agent`; whole-peer actions are single words (`crawl`, `sync`, `serve`, `refresh`). Options are named (`--port`, `--leave`); `ls` and `show` are shortcuts for `title list` and `title show`.
* **Usage:** placeholders are in capitals, named for what they mean rather than their type (`URL`, `--port PORT`). `-h` or `--help` shows usage, of one noun or action if given, as does a noun alone; a command line that isn't one shows the same and exits with status 2.
* **Downloads:** `title download` fetches a title's, a season's, or an item's files into a directory (the current one, or `--to`), under their paths in the repository that held them, so the directory, served and crawled, names them alike: in the rendition given, else the one most of its items have; from its copies in copy racing's order, the next tried when one fails; into `<path>.part`, resumed by a range request, renamed once whole, and never written past the file's size; a file already there at its size is kept; and only paths within the directory (a crawling member's device chose them).
* **Added peers:** peers added by URL are kept in `local`, on that device only; `sync` without a URL, and `refresh`, pull from every peer discovered or added.
* **Background:** on macOS, `agent add` loads two launch agents (`com.rbrian.cinematheque.serve`, keeping `serve` running, and `.refresh`, syncing with peers discovered or added, then crawling, hourly), logging to `~/Library/Logs/Cinematheque`.

## Apple players

* **Structure:** one `App` and root view (no home, setting up, or browsing; at launch and once set up, naming, serving, and refreshing), over a shared model, cover cache, playback session, title presentation (facts, runtimes, episode names, Play labels, Start Over (a rewind symbol before Resume, as a player's timeline starts at its leading edge, playing what it would from the beginning), the rendition to play, and the watchlist and watched marks, the watched one showing its state, Watched or Unwatched, which pressing toggles), shelves (Home, Movies, Series, Watchlist, and Played, a smart folder of everything with a playhead, in progress or watched, from which Remove from Played, in a tile's context menu, removes its playheads (a season's, on the Mac; a whole series', on the Apple TV, which shows one tile per series): their tiles, search, counts, and empty text; the Mac's sidebar shows all but Home), and debug launch options, with setup (`SetupView`: one form on the Mac, tvOS-style steps on the Apple TV) shared too, and each platform's `Browser` and the rest apart (`#if os(...)`), and what else differs (the home, default names) in `Platform`, by one Xcode target (Xcode 27's `project.xcproj` format), whose build phase builds the core for the platform and each architecture and links it into one object exporting only the C interface, so the compiler runtime Zig bundles can't clash with Xcode's.
* **Setup:** pairing by a code this device shows (`OfferedCode`), to be another of the user's devices or to join someone's library, or creating a library. On the Mac, one form: Pair with Your Other Device and Ask to Join, each showing its code in place, and Create Library. On the Apple TV, as tvOS apps set up: the app's name over three large choices (I Use Cinematheque on Another Device, and Join Someone's Library, each a screen showing its code; Start a New Library). Neither app shows or takes keys; the command-line peer still does.
* **Playing** (`FadingIn`), on every platform: fading to black while the stream warms up, paused (loaded, sought to the playhead, less 4 seconds when resuming, and prerolled), then playing and fading to the picture as its sound rises from silence, and when left, fading to black as its sound falls, its playhead where that fade ends, so resuming replays the 4 seconds before it; a curtain over both (`Curtain`), each fade 0.5 seconds (`Platform.fade`); a download on this Mac from its file, first and unraced; else streaming from the repository: first from the copy whose server answers first (copy racing, `cq_race`, in the core, for every player), each copy's asked at once (`HEAD`, 1.5 seconds; one that didn't answer in the last 10 minutes, as this device notes, asked last), so a peer that's asleep costs a second or so, not a network timeout; then trying the item's other copies in turn (the rendition's, then its other renditions') when one doesn't load, as on a drive that's unplugged; starting at the playhead unless watched, saving it every 10 seconds past the first 10 and where it's paused or left, marking an item watched at its end, and going on to the next.
* **Serving:** the apps serve while they run, on the port they got last, so other devices sync with them directly; and they sync quietly (without showing it as an activity) a minute after they last synced, and whenever they come to the front (as an Apple TV app returns from the home screen, never relaunched), so what other devices change arrives without a refresh. After a change of their user's (pausing or leaving playback, a watched mark, the watchlist, Remove from Played), once changes stop for a second, they sync, which pushes the change to every peer at once; and when a peer pushes its changes to them, they reload at once. For diagnosis, each shows the last exchange each way in one line: what it received, from which peer, and what it sent, to which device, and when.
* The project follows Xcode's recommended settings but for script sandboxing (the core's build phase), the App Sandbox (the home it shares with the peer), the hardened runtime (until signing for distribution), and its macOS 15 minimum. A developer's signing settings stay in an ignored `Local.xcconfig`.
* The bundle's `Info.plist` allows plain HTTP and Bonjour on the local network.

## macOS player

* **Browsing:** shelves (Movies, Series, Watchlist, Played, Downloaded, what this Mac keeps, and Watched Downloads, those of them watched since: waiting for their space to be needed, marked with an hourglass, or the only copy, marked in orange, for a person to delete or keep; no All), searchable; a grid of covers in fixed cells, movies 2:3 and each series' seasons square under its name (each season's cover whole, fit and centered, here and in the inspector), each with a star at its top leading corner if on the watchlist, a watched mark (top trailing) or progress bar, and a download mark (bottom trailing) if this Mac holds any of it, or a Watched Downloads mark; a cover shows its placeholder until loaded (without one, a color with its title), then replaces it at once, without a fade. Each shelf has its own scroll view, and returns to its topmost title when shown again; the grid keeps that title at the top as its width changes (e.g., the inspector opening or closing) and its rows reflow. A title, not an offset, which a change in width would move; the topmost is the first at least half on screen. Covers are fetched by range request, scaled with ImageIO off the main thread, and cached in memory and in the app's caches.
* **Inspector:** for the selected tile, a larger cover, Play or Resume (a movie, or a season's episode in progress, the latest if several, else its next unwatched, with the rest of the season queued), a rendition picker, a movie's progress (and each episode's, in its row) with a clear button (`arrow.counterclockwise.circle.fill`) beside it, which forgets the position, not the watched mark, so Resume becomes Play, the watchlist and watched marks, metadata, a movie's versions, and a season's episodes, each playable, described on demand, under a heading with Play from First Episode (a link, the rest queued, shown only when Play would start elsewhere); downloading: a movie's Download (then Downloading…, or Downloaded, and once watched, waiting or the only copy, with Keep, and a trash button), a season's Download menu (Download Season, Keep Next Episodes: Off, 1, 3, 5, or 10, and removing the season's downloads), with how many are downloaded and kept, and each episode's mark and context menu (Download, Keep Download, Stop Keeping Download, Delete Download, saying so if it's the only copy). Season 0 is Specials.
* **Crawling:** while a crawl runs, the grid reloads as it commits (polling `cq_data_version` each second), and the tiles on screen are described first.
* **Playing:** in the library's window, filling it over the browser (which keeps its place), with the toolbar hidden and the title bar transparent but its window buttons kept, and Back (or Escape, or the queue's end) returning to the library, its black fading away to it, Back showing only as the player's controls do, while the pointer moves and for 3 seconds after, beside what's playing (a movie's name, or a series' over the episode's code and name), since the title bar hides its title; with ⌘ held (⌘-click, ⌘-double-click), in a window of its own, titled with what's playing, as many as wanted. Either way, Space plays or pauses, F toggles full screen, M mutes, and the left and right arrows skip back and forward 10 seconds (the Apple TV's remote does as the system's player does), in an `AVQueuePlayer` in AppKit's `AVPlayerView`. Player windows aren't restored at launch.
* **Settings,** by what people do, with addresses under Advanced, in four tabs: People (members by name, with the founder, you renamable in place, and devices nearby of the library whose users aren't members yet, to Add); Devices (your named devices, this Mac among them, each renamable in place (tvOS tells apps only a generic name, Apple TV) and, but for this Mac, removable; sharing the library on the network while the app runs; New Devices, always shown, listing new devices nearby offering to pair, to be yours or to join, each with a field for the code it shows, pairing it (and adding a joining one's user) and moving it, animated, into Your Devices (or People); under Advanced, peers by address, e.g., beyond a NAT); and Sources (Add Folder… and Add Server…, as buttons, not a menu; folders on this Mac, served at `http://<Mac>.local:<port>/<folder>/` while the app runs and kept in the app's settings (one that isn't there, on a drive unplugged or a share unmounted, say, is shown as not found, and served empty, so a crawl marks it absent and its titles show dimmed until it's back), and network addresses; readable names, e.g., "art › Movies › 2160p"; a rendition and names to skip under Advanced; a repository's absent folders, as unavailable, each with when it went and Forget; devices' downloads not listed); and Downloads (the folder, `~/Movies/Cinematheque` unless chosen, as Apple's TV app keeps `~/Movies/TV`, served at `/downloads/`; what it holds and the space free; progress while downloading; and whether watched downloads go at once). Names are ones everyone in the library sees. On launch the app names this Mac and you (the computer's name, the account's first name) if they have no names. If it must serve on another port, it moves its folders' repositories there. Long operations run off the main thread.
* **Toolbar:** the sidebar's toggle and the shelf's title at the leading edge; the inspector's toggle (⌥⌘I) and search at the trailing. Refresh Library (⌘R, in the View menu) syncs, then crawls; at launch, if there's a library, the app serves it, syncs, names itself if need be, then crawls; syncing before writing anything, so a device whose replica was lost learns its own writes back first.
* **Status bar:** along the bottom of the grid, floating over it: the shelf's counts ("4,000 movies"; "12 of 4,000 movies match …" while searching), or what went wrong, at the leading edge; what a long operation is doing and how far it has come, with a progress bar, at the trailing, or when none is, the last exchange with peers each way ("Received 3 changes from firefly 1m ago · Sent 12 changes to Den just now", counting operations), unless a problem shows. It fades out 3 seconds after it last changed, unless something is running or wrong, and comes back when the pointer nears it; floating, so fading moves nothing.
* **Modelessness:** no modal alerts, after the original Macintosh guidelines. What goes wrong shows in the status bar (and in a bar along the bottom of Settings), in words, each source by its name in Settings and the core's error said plainly (e.g., "Crawling failed for art › Movies › 2160p (and 5 more): the server has nothing at that address."), until dismissed or until the next action of its kind (refreshing, changing the library, reading it) succeeds.

## Apple TV player

* **Home:** in the caches (the core's default on tvOS), the only place tvOS lets an app keep files, which it may purge; the seeds (`identity`, `user`, `library`) are kept in the Keychain too, and put back at launch, so a purge loses only what syncing and crawling rebuild.
* **Refreshing:** at launch, naming itself (the Apple TV's name) if it has no name, serving (so its playheads and watchlist reach the user's other devices), then syncing with peers found by DNS-SD, then crawling the repositories itself.
* **Exchanges:** the last exchange with peers each way, shown for a few seconds in the corner after each.
* **Shelves:** a tab bar of Home (Continue Watching, then the watchlist), Movies, Series (a cover per series, its progress over every season's running time), Watchlist, Played, and Search; covers six to a row, as cards, with progress and watched marks, and a star if on the watchlist (a series', if any season is).
* **Pages:** a movie's, over a blurred backdrop of its cover: Play or Resume, the watchlist and watched marks, versions, and its description; a series': its seasons (the first not watched through, specials last, outlined; each cover whole, fit and centered in its square), Play for the season's next episode (before Resume, Start Over, on both pages), and its episodes, described as the season's shown.
* **Playing:** full screen in `AVPlayerViewController`: the page (and the tab bar) fades to black while the stream warms up, then the player is presented over it, unanimated (black over black, were it animated), still paused while the display switches to the video's frame rate and range (asked for by the app, not the player, if Match Content is on), which blanks the screen; then it plays, its picture fading in as its sound rises. Menu (Back) fades it to black as its sound falls before it goes, over the black page, which then fades back in, and gives the display back its own mode; its info panel showing each item's title and description, on the shared playback session; the rendition is the best it plays: MP4, MOV, or M4V (not MKV or ISO), up to 2160p on a 4K display, else up to 1080p.

## Debugging

* Debug builds take launch options for driving the app unattended (in a VM by `open --env`; in the tvOS simulator by `simctl launch`, each prefixed `SIMCTL_CHILD_`): `CINEMATHEQUE_CODE_FILE` (a file each pairing code offered is written to, for a test to send from another device), `CINEMATHEQUE_SELECT` (a tile, e.g., `t/s/firefly/-#1`: selected on macOS, its title's page opened on tvOS), `CINEMATHEQUE_TAB` (tvOS: a tab, `movies`, `series`, ...; on both, in setup, a step, `link` or `joinOther`, offering its code), `CINEMATHEQUE_DOWNLOAD_FLOOR` (the free space downloads keep, in bytes, for a VM's small disk; any build, read by the core), `CINEMATHEQUE_PLAY` (once a launch: a URL to play on macOS, with `CINEMATHEQUE_ITEM`, its item key, for its playhead; any value on tvOS, to play the opened title).

## Implementation

* Zig 0.17+ for the core and the peer, with no dependencies beyond the system's SQLite and DNS-SD. Whatever waits (networking, sleeping, SQLite waiting out another connection's write, DNS-SD waiting for results) does so through Zig's `Io`, so it can be canceled; only what `Io` can't reach blocks outside it (SQLite's own disk I/O, the system's name lookup).
* SwiftUI for Apple players.
* SQLite for each peer's replica.
* Tests: the core's unit tests (`zig build test`), [peer/test.sh](peer/test.sh) (two peers and more, end to end), screenshots of the macOS player in a macOS VM (terrarium's `macos-27.2-quiet`), and of the Apple TV player in the tvOS simulator (an Apple TV 4K, 3rd generation).

## Scale

100,000+ video files: 4,000+ movies, and 500+ TV series of up to 30 seasons of up to 50 episodes.

## Risks

* App Review may resist publishing a library that encroaches on Apple's own, all the more so one that serves media.
* Outside metadata comes from providers outside Cinematheque, whose sources' terms (e.g., TMDB's charge for commercial use, IMDb's datasets for personal use only) bind them, not Cinematheque.
* GPL tools (`HandBrakeCLI`, GPL builds of FFmpeg) must run as separate processes, never linked, or they bind the license of the players and the shared core.
