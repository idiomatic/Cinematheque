# Cinematheque

Local-first video libraries. Players on Apple devices, macOS, Linux, and Windows browse shared libraries and play each video from any source that holds it. There is no central server: each library's titles, metadata, and people's data replicate among devices, so every device works offline and catches up when it reconnects.

This file specifies what's built. How operations are written, merged, and synced, the keys and fields the library writes, and the measurements behind the design are in [ARCHITECTURE.md](ARCHITECTURE.md); plans and open questions in [DEVELOPMENT.md](DEVELOPMENT.md); outside specifications are indexed in [docs/specifications](docs/specifications/README.md). Agents working on it at once coordinate as `.coordination/README.md` says, kept out of Git.

## Lexicon

One word for each thing, in the spec, the code, the command-line app, and the apps alike; stored keys and fields keep their names as data. The apps show people only the words marked † (in everyday senses); the rest are for developers, and the apps say what they mean instead.

* **Source†:** anything serving videos over HTTP (a NAS, a web server, a folder a device shares); a device's downloads are one, though not listed. Not "repository."
* **Copy†:** a file of an item, in one quality, that a source holds (stored as `held:<source>`). Not "holding."
* **Device†:** a running Cinematheque with keys of its own (an app, the command-line app); the one it syncs with is the other device. Not "peer."
* **Person** (shown as people†): a human, with a key and devices; a member†, once admitted to a library. Not "user" (except in what's stored: the data directory's and the Keychain's `user` seed, and certificates' and names' `user` fields).
* **Progress:** where a person stopped in an item, and its watched mark. Not "playhead"; how far a long operation has come is its steps.
* **Unavailable†:** a folder that held files and lists none (stored as `absent:`). Not "absent," "missing," or "not found."
* **Join†:** what a new device does to come into a library, by a code it shows; a member's device adds† it, as another of its person's devices (pairing† it) or someone new's (a new member). Not "link."
* **Data directory:** a device's own directory, of its keys and replica. Not "home," which is taken for `$HOME` (except in what's stored: the Keychain's `com.rbrian.cinematheque.home` items).
* **Share†:** what a device does with its library and folders (its server serves them).
* **Delete†** takes files off a disk; **remove†** takes something out of a list or the library (as an unavailable folder's videos); **forget†** discards only what's known (as an address added, or where a person stopped).
* **Download†:** files coming to the device a person is using: in the apps, its own downloads; in the web client, a file to the browser's computer. **Keep†** is the web client's word for the server's downloads, held for other devices to play from; it names the server only in passing (as "Kept"), since a person minds the computer in hand.
* **Download next†:** a series' next episodes, as it's watched (one of its choices of episodes to download).
* **Quality†:** one encoding of an item (stored as a source's `rendition` field). Not "rendition." **Version†:** an edition (a director's cut); **origin:** a quality's Blu-ray, web, DVD, or HDTV token.
* **Sync** and **crawl:** syncing goes on by itself, shown only as catching up† where it explains something (a removed device leaving); crawling is shown as looking for new videos†, which Refresh Library† does (syncing first).

## Components

* [core](core/README.md): the Zig library, and a static library with a C interface ([cinematheque.h](core/include/cinematheque.h), a Swift module by its [module map](core/include/module.modulemap)) whose results are JSON with every string valid UTF-8 (a name that isn't, from a Latin-1 file, gets U+FFFD for its bad bytes, so no player refuses a whole result) (see [Core interface](#core-interface); documented in [core/include/README.md](core/include/README.md)).
* [cli](cli/README.md): the command-line app, `cinematheque`, for macOS and Linux.
* [apple](apple/README.md): the Apple players, in SwiftUI: one multiplatform app, `com.rbrian.cinematheque`, for macOS 15 or later and tvOS 18 or later, and as a prototype, iOS 18 or later on iPhone (see [Apple players](#apple-players)).
* [tools](tools/README.md): scripts alongside the apps, such as [debt.py](tools/debt.py)'s report of code debt.

## Core interface

* **One function per action:** no argument chooses among actions (adding or removing, on or off); a caller holding a state picks the function.
* **Arguments** are C's own: arrays as a pointer and a count, records as structs, kinds as enums (a value none names refused), an absent integer -1; only results are JSON.
* **Threads:** its functions belong to one thread, except long ones (crawling, syncing, describing, and downloads' configuring, deleting, and reconciling) and reading the tiles and sources (`cq_tiles`, `cq_repos`, the whole catalog, which the apps read off the main thread as a long operation commits); each of those runs on a connection of its own. Only one connection writes as the device at a time, and the main one catches up (`Replica.refresh`) before acting. Leaving (`cq_leave`) refuses as `Busy` while another thread's connection is open, and none opens while it leaves, so the apps stop reconciling, start nothing, and wait out what's under way first. Strings passed in are copied if kept.
* **Long operations** commit as they go; `cq_data_version` changes when they have, `cq_steps` tells how far one has come (its phase, and steps done of how many), and `cq_prioritize` names titles (e.g., those on screen) for a crawl to describe first. `cq_crawl` crawls every source (`cq_crawl_full` listing every directory afresh); `cq_crawl_due`, for a refresh not asked for, crawls those no device crawled within the library's interval, which `cq_crawl_every` sets and `cq_status` gives.
* **Serving and syncing:** `cq_serve` serves the library (and folders, each at its own path) on a task of its own until `cq_stop_serving` or `cq_close`; `cq_served` tells of the last sync it served (to which device, how many operations), and `cq_received` of the last push it took (from which device, how many operations won). `cq_sync` syncs with every device found or added, and `cq_sync_with` with one; their results name each device as it advertised itself, with how many operations were pushed to it; `cq_sync_known` syncs with the devices the last such sync found (and those added), without looking for them again.
* **Pairing:** `cq_pair_offer`, `cq_pair_check`, and `cq_pair_stop` offer a new device to be added; `cq_pair_person` adds one as another of this person's devices, and `cq_pair_member` as a new member's, each returning its person's key and its own; `cq_name` names another device, as one just paired.
* **People and devices:** `cq_status` tells whether this device is paired as another of a person's devices, and how many other devices its person has. `cq_set_person_name`, `cq_set_device_name`, `cq_devices`, `cq_nearby` (devices found nearby, with names, and addresses added), `cq_device_address_add`, and `cq_device_address_forget` let apps show people and devices by name. `cq_remove_progress` removes this person's progress in an item, `cq_remove_device` another device, and `cq_remove_self` this one, as it leaves.
* **Lists:** `cq_lists` tells this person's lists, by name, with their titles, then other members' shared ones; `cq_list_create` makes one, returning its ID; `cq_list_rename`, `cq_list_remove`, `cq_list_add_title`, and `cq_list_remove_title` change them; `cq_list_want` puts a title not in the library yet on one, as a placeholder, and `cq_list_edit_want` changes one; `cq_list_share` shares one with every member, and `cq_list_stop_sharing` makes it its person's alone again.
* **Downloads:** `cq_downloads_configure` sets where a device keeps downloads and the URL it serves them at; `cq_download` and `cq_download_next` say what to download; `cq_download_remove` deletes; `cq_downloads` tells all of it (what's held, which are the only copies, wanted, and chosen, free space, and how far reconciling, and the file under way, have come); `cq_download_sizes` tells what downloading a title, season, item, or series' choice would come to (its files' total size, and what of it isn't here yet); `cq_reconcile` (long) fetches and deletes to match, and a call while one runs asks it to run again and returns; `cq_reconcile_stop` stops it, the file under way kept to resume; `cq_downloads_hold` holds new downloads back while a stream plays, and `cq_downloads_resume` lets them go.
* **Version:** `cq_version` tells what the build is, as `/version` serves it (see [Sources](#sources)); the Mac's About shows what it was built from after the app's version, as `cinematheque --version` prints both.

## Devices

* **Players:** every client, each able to sync and crawl as well as play.
* **Refreshing:** every device syncs with the others first, then crawls, so the catalog others have crawled and described arrives first and the crawl adds and describes nothing unchanged. A crawl records when it was, on its source (`crawled`). A refresh not asked for (at launch, or on a timer, which first waits a random time so devices on timers don't refresh together) skips a source any device crawled within the library's interval, whose copies syncing brought, or every source if the interval is Manually. The interval (`settings`' `crawl`, for every device) is every hour, 3 hours, day (the default), or week, give or take a 24th of it, drawn afresh each time so devices that crawled together don't come due together. So a consumer NAS's disks spin up for crawling no more than chosen; Refresh Library and `crawl` crawl them all, for when a person knows there's something new.
* **Static servers:** sources running no Cinematheque code, such as a consumer-grade NAS or a web server (Caddy, nginx, Apache).
* **Desktop devices:** macOS, Linux, and Windows players. They are sources too, sharing their local and downloaded videos, and differ from static servers only in what they hold and how long they stay online.

## Identity and membership

* **Data directory:** `~/Library/Application Support/Cinematheque` on macOS, `$XDG_DATA_HOME/cinematheque` (`~/.local/share/cinematheque`) elsewhere, or another by `--data` or `CINEMATHEQUE_DATA`, which the C interface, and so the app, honors too. It holds `identity` (the device's random seed), `user` (the person's seed, if paired as another's device), `library` (the founder's person key), and `replica.db`, all its owner's alone (made so on opening, whatever an older build left).
* **Keys:** a device's keys derive from its seed, and its person's from the person's seed, which the person's devices share; a device not paired as another's derives its person's seed from its own. The person's seed is a secret, given to another device only by pairing, and never shown.
* **Pairing:** a new device, before it has a library, shows a 6-digit code and offers to be added, serving `/pair` and advertising `pair` (`new`) by DNS-SD. A member's device, given the code, has its person decide whose device it is, since handing its person's seed to someone else's device would let it act as them. It sends the founder's key and, if adding it as its person's, the person's seed (else zeros), sealed with a key both derive by CPace (ristretto255, SHA-512) from the code, so an eavesdropper learns nothing and each attempt tests one guess. The new device answers with its person's key and its own, sealed the same way. A new member's person is added as a member. The member's device names the new device, under its person, as it advertised itself, until it names itself (a generic name, as tvOS gives apps, by its host: `Not-Your-AppleTV.local` as "Not Your AppleTV"). After 3 wrong codes from one address it stops answering that address, and after 30 in all, every address, until it offers again with a new code: so no one host can stop it, and guessing gets 30 tries at a million codes.
* **Certificates:** a device's first write is its certificate, its person's signature over the library and the device key; its private stream has one of its own, which travels on that stream. Before writing, once per connection, a device writes afresh any of its own that's missing or invalid, at the current time so it wins. The apps, on opening the library, rewrite one they hold that doesn't verify without waiting to write, but never write a missing one first (a device whose replica was lost must sync first). Only other devices would notice an invalid one, by refusing the whole stream.
* **Library:** its ID derives from its founder's person key. Members add people to a set; any member may remove another, except the current founder, for good (they come back as someone new).
* **Handover:** the founder may hand the library over to a member, staying or leaving. Handovers are a numbered chain, each valid only if written by the previous generation's founder, so devices agree in any order.
* **Removal:** any member may remove a device without its person (except the founder's devices, which only the founder's may remove, as the founder's only device leaving would forget the founder), or a member with every device of theirs it knows. A removal only stands or tightens (the lower cutoff wins), so none can be undone. Each of a removed device's streams (its own and its private one) is cut off where the remover had seen it (`revoked`, a field per stream): writes through there stand, later ones are refused, and devices serve it no more. A removed member's device the remover didn't know isn't admitted.
* **Repair:** a device that took later writes before hearing of a removal drops them, notes their fields, and repairs them from a device that refused them, fetching just those fields' winners with one shared proof per batch; a write only it held, which lost to a refused one, is lost.
* **Leaving:** a removed device is told so when it next syncs: the device refusing it signs a refusal (`removed`) over the library, the device, and its request's time, which it believes only if a member certified the signer and it doesn't know the signer removed. It then forgets the library and its identity (`cq_leave`; on tvOS, the Keychain's seeds and the Top Shelf too), stops the refresh under way, and returns to setup, saying why, to pair again as a new device. It still holds its person's seed, so keeping it out for good would take a new person seed. A device may also leave of its own accord. It removes itself, cutting its streams off just past that removal (first, if its person is the founder and it's their only device, handing the library over to a member, who's asked for); syncs so another device takes the removal (refusing to go on if none can be reached, and retried without writing it again); then forgets as above. With no one else in the library, it only forgets.

## Replication

* **Operations:** each writes one field of one key. Fields merge last-writer-wins by hybrid logical clock, ties broken by device key (handovers earliest-wins, so one stands once made); `members` merges by causal length, a removal outranking any addition, so it's for good. An operation dated more than a day past the receiver's clock is refused.
* **Limits:** a device writes no key or field over 64 KiB, nor a value over 4 MiB, as other devices refuse them.
* **Batches:** a device signs each batch of up to 1,024 consecutive writes (a transaction's) once, with Ed25519, over its library, stream, range (first sequence number and count), and the root of a BLAKE3 Merkle tree of their encodings, so any operation, or set of them, is verifiable by proof, and a batch can't be presented with another range.
* **Storage:** SQLite holds each field's winning operation (as columns, from which its encoding is rebuilt), interned device keys, signed batches, a version vector of each device's highest sequence number covered, fields awaiting repair, and the device's own state (`local`, e.g., crawl snapshots). It runs in WAL mode, and connections wait up to 10 seconds for one another's writes, since the command-line app's `serve` and `refresh` share its replica.
* **Sync** runs both ways, started by either side. A device asks the other which device it is (`GET /sync`), then POSTs to `/sync` a request for that device alone, signed by its own, with its certificate, the time, the other's key, a repair's field list's digest, and its version vector. The other device refuses a request for another device, and the device refuses a response from any but the one asked, so a request a device was sent can't be replayed to another. Bodies are sealed (an X25519 key pair for the request alone, with the other's key; ChaCha20-Poly1305 in numbered chunks, the last marked), so only the two devices read them, and the request is opened and checked before the rest is read or the replica opened. Each answer's key is salted afresh by the device answering, so a request replayed is never answered under the same key and nonces. The other device answers members only, within ten minutes of its own clock, with frames: per device, its winning operations above the vector, grouped by batch, each batch with its signature and the leaves of operations not sent; then its vector, which the device adopts only under the sender's signature (`S`) over the request's signature and every frame's header, so a response is believed only from the device that sent it, for that request, with no batch left out; and, in headers, its own device key and certificate.
* **Push:** the device then pushes what the other lacks: a second POST to `/sync` (with its own content type) of a signed request and the frames above the other's vector, signed as a response is, which the other applies as it would a response. It leaves out private streams not the other device's person's. So a device that can reach another that can't reach it (behind a NAT) syncs both ways. Frames are gzipped, and a body is read whole (up to 256 MiB) before it's applied, so a slow sender holds no write lock. A refused push fails the sync, as a refused pull does.
* **Own private stream:** a device takes its own private stream's batches as its person's even before the certificate arrives, so a device whose replica was lost (as tvOS may purge one) gets its progress back from its person's other devices.
* **Admission:** a receiver applies a batch only if its device's certificate names a member; else it holds the batch (checked once, each costing at least 4 KiB of what may be held) until the end of the response, then rejects it without claiming it in its vector. It refuses operations past a removed device's cutoff, cutoffs past any sequence number a stream could reach, handovers not from the previous founder, private data not from its person's private stream, operations of the wrong kind for their keys, certificates but a device's own or (for a private stream) its writer's person's when none held names another, a shared list's fields but from its owner's devices, and batches overlapping one held. It takes a response's vector only from a member's device, and never for its own streams.
* **Private data:** a person's progress (`p/<person>/...`) is written on each device's private stream, with its own key and numbering. Devices send private streams only to the devices of the person they're of, and leave them out of the vectors they send others, so private data travels only directly between a person's devices.

## Library

* **Keys:** `t/<m|s>/<normalized title>/<year or ->` for a title. Below it: `/v/<edition or ->` for a movie's version (its `edition` field naming it as written); `/e/s03e17` for an episode (`/e/s2024e0312` for a dated one, a season a year, as Plex has it; then `/v/<edition>` for an episode's version; `/e/s00-<normalized title>` for a special without a number, its `title` field naming it); `/p/<n>` for a part; and `/r/<quality>`, whose `held:<source>` field records the file's path, size, and modification time, empty once no longer held. A title's key derives from its parsed identity, so devices crawling independently agree.
* **Naming:** the parser reads Plex, Jellyfin, and Kodi conventions and download names: ID tags, years (the last year ends a title), editions, parts (after the year, and after an edition's name: `- Extended Part 1`), extras, `S01E02`, `1x02`, air dates, season folders, yt-dlp's `[youtube-ID]` tags (a dated name's words before one being the video's title, unread), and Kodi's compact codes (`Show 317 Title`) right after the series' title from the enclosing folder. Dots between digits are a title's own (`11.22.63`); a name of numbers alone without a year (e.g., a camera's) goes to review. A numberless file beside a series' episodes whose name extends the series' (`Babylon 5 The Gathering`), or in a `Specials` folder, is a special (season 0).
* **Qualities:** a file's quality is the first folder within its source, as named, if the source names qualities by folder (`Movies/HQ 1080p30 Surround/Alien (1979).m4v`; that folder isn't read as the file's name); else its source's, if named; else its name's technical tokens, canonically (resolution, origin, codec, dynamic range, e.g., `2160p remux hevc hdr`); else unknown (`-`). Two files of one quality in one source are numbered (`~2`) as duplicates, shown as "1080p 2" (an unknown one's "Other 2").
* **Review:** among titles some source holds, close matches (a year off by one, missing, or with transposed digits; the same year, the same digits, and a spelling within two edits; or only diacritics differ) and duplicates. An alias (`aliases`) records that one title key is another's; it replicates, and an empty one undoes it.
* **Progress:** per person and item (version, episode, or part), above qualities: position and duration in milliseconds, and watched, set on reaching the last 5% or by hand. A position in the first 10 seconds isn't kept: recording one empties the position and duration (not the watched mark), so stopping at the start sticks. Marking an item unwatched empties its position and duration too, so it plays from the beginning; removing progress empties all three.
* **Describing:** after each crawl, one file per movie and per season, across every source, describes it, unless what it last read is unchanged: its cover's file's size and modification time (the video's too beside a poster, as a tool adding a sort name changes only the video), and what describing reads, by version (so a library described before describing read more is described again once, by whichever device crawls it first). Else the best file describes it: a sidecar, then an MP4, then another file; a movie's standard version before its editions. Describing runs after crawling, so titles show before covers, with 16 workers, prioritized titles first, committing every 24 jobs or 750 ms. A network failure is retried next crawl; a file that isn't a readable MP4 records an empty cover, so it isn't reread until it changes. MP4 metadata (each text up to 64 KiB, and up to 256 atoms walked at a level) fills a title's `description`, `genre`, `released`, `network`, and `sort` (what it sorts as: a movie's `sonm`, a show's `sosn`), and an item's `title` (an episode's), `description`, and `duration`. Other episodes are described on demand, and other versions too (their durations alone, so an edition's file doesn't speak for its movie). Each item records the file it was read from (`read`: its source, path, size, and time), so players describe it again once that file changes (`described`, in views), as retagging it does.
* **Covers:** from a sidecar image by Plex, Jellyfin, and Kodi convention (`poster.jpg`, `folder.jpg`, `<movie>-poster.jpg`, `season01-poster.jpg`, a season folder's `poster.jpg`), else an MP4's, read by range requests that walk atom headers to `moov` and read `udta` whole (about 8 requests). A cover is recorded as a byte range of the file (`art`, or `art:s01`... for seasons, on the title's key), so players fetch it with one range request; images don't replicate. Its placeholder does: `thumb` (or `thumb:s01`...), a ThumbHash in base64 of its JPEG's DC coefficients (an eighth-size image, decoded without a full decode), or `-` for another format, rendered by `cq_thumbhash`. A cover described without one gets one from a single range request.
* **Tiles:** for browsing, a movie or a season (a season without a cover takes its series'), with this person's progress: watched if every item is, else the share of its running time played (watched items whole, so one stopped in its last 5% counts in full, and items partway to their positions; an item of unknown length takes the average of those known), with the milliseconds elapsed and the runtime. A tile also has how many items it holds; whether any item has progress (begun), which puts a season with an episode partway on Home; and its title's place in each order ([order.zig](core/src/order.zig)):
  * by title: its `sort`, else its name less a leading "The", "A", or "An", without case or Latin accents, numbers as numbers, then year;
  * release: `released`'s date, else the year;
  * when added: `added`, on the title's key, written once, by a crawl that finds the title in a source crawled before; else, for what a source's first crawl found, there all along, its qualities' files' earliest modification time, as listings give it (RFC 3339, Unix seconds, or an HTTP date; ctime or creation time is in none);
  * when last modified: its files' latest modification time (not a device's downloads', whose times are when they were fetched);
  * when this person's progress in it last changed.

  Each is counted from what comes first in the order's usual direction (A to Z, the newest). A series' seasons share their series' place (added when its first was, watched when its last was). A title with nothing to order it by has none, so it goes last either way.
* **Lists:** per person, private like progress, sets of titles (a Watchlist, Favorites), by name ([lists.zig](core/src/lists.zig)).
  * `p/<person>/lists` has a field per list's ID (16 random hex digits) naming it, empty once deleted, for good. Each list's titles are at `p/<person>/list/<id>`, a field per movie's title key, or per season (`<title key>#<season>`, each season listed on its own), `1` while on it.
  * A title not in the library yet is a placeholder (wanted), `w<TAB>name<TAB>note` (the name as typed; a note such as an article's address), keyed from its name and year (a series', its season, the first unless given) as its file will be, so it's on the list as it comes, with nothing to backfill, matching only if its file is named alike; devices too old to know placeholders show only `1`s. Players show a placeholder not yet come as a dimmed tile of its own, "Not in library", taken off by Remove from List. The Mac adds one by a list's Add Missing Title… (a movie, or a series' season: its name, year, and note), its inspector showing it, with Edit…; the web client, by the ＋ beside a list's name, and changes one by the ✎ on its tile. The Apple TV opens one, pressed, on a page of its own: its fields, each changed in place (on the full-screen keyboard, its kind by pressing), and Remove from List; but leaves them out of the Top Shelf. Changed, one is keyed afresh, its old key taken off in the same change, on every list of its person's it's on.
  * The Watchlist is a list like any other, renamed or deleted as freely, but keeps its titles where they always were (`p/<person>/watchlist`, its ID `watchlist`), named "Watchlist" until renamed, so devices too old to know lists still show it.
  * A list shared with every member (confirmed first, as their devices keep what they receive) moves its titles to a public key of its own, `l/<owner>/<id>`, beside its `name`, taken only from its owner's devices; its owner's index still names it. Its mode is a log of changes (`mode:<random>`, `shared` or `private`, each written once, the latest current), so the mode as of any write can be told however they arrive, for lists every member changes, to come. Made private again (unconfirmed, as sharing again undoes it), its titles go back and the public copy is emptied, hiding it, not recalling it.
  * Players show other members' shared lists after their person's own, read-only, as theirs ("Avery's Watchlist", its ID `<owner>/<id>`), every shared list marked with two people. Only a person's own lists are in Lists menus, and star a title. Devices too old to know shared lists show a shared one as empty.
* **Names:** people's and devices' (`n/<key>`'s `name`, and a device's `user`, its person's key), set by any member, shown in place of keys.
* **Views:** what players show comes named and decided, so no player reads a key or decides alone ([views.zig](core/src/views.zig), for the C interface and the web client alike):
  * a title's items in order (each season's episodes by number, specials last), and its seasons in that order;
  * which item Play plays of each season or of a movie's versions (`next`: the latest in progress, else the first unwatched after the last watched, else the first unwatched, else the first);
  * each quality's resolution (`height`, for players to rank what they play by);
  * items with an episode's season and number, a dated one's air date, a label ("Episode 3", "Special", "March 12", or a version's name, "Standard" or its edition; a part's with its number, "Part 1" or "Director's Cut, Part 1"), and a name in a list ("3. Title");
  * each quality's short name for a picker: its resolution, with HDR if it says so ("4K HDR"), or Other for one of unknown quality; where two of a title's would read alike, each adds what else its full name says, but not options (`--colorspace=bt709`) unless only they tell them apart ("720p Very Fast").
* **Facets:** titles held by some source, counted by kind, decade, and quality.

## Sources

* **Settings:** a source is a URL (percent-encoded as typed; http or https, with a host, and no query or fragment, else a device takes it for none, as any member may write one), with where its files' quality comes from (their names, the first folder within it, or one name: `quality-by` and `rendition`; a `quality-by` this device doesn't know, a newer one's, keeps it from crawling the source rather than guessing), and a prefix of names to skip (none by default, as a prefix skips titles that start with it too), changeable later (applied at the next crawl). Its ID is a hash of the URL, which its `url` must match (or be empty, once removed), and that stands from the device that wrote it, the only one whose `managed` is taken, so no member can take another's source over or stop its crawls. Removing it clears its settings and copies for every device, and the remover's crawl snapshot.
* **A device's downloads:** a source of its own, `managed` (a replicated field), which no device crawls (the Mac app's, and the command-line app's with `serve --downloads`). Each file fetched is recorded as its copy in the very quality it came from, so devices see it and play from it. Files go under their paths in the source they came from, into `<path>.part` resumed by a range request, never written past their size, and only within the folder, at a video's path with nothing hidden along it, never replacing a file of another size there but one its own downloads recorded. It deletes, keeps, and forgets only the copies of its downloads it recorded itself, as another member's device may write some too. While a stream plays on the device, no download begins (one under way finishes), so as not to slow it. A file under way that stops being wanted (deleted, or its series' choice changed) stops as its next mebibyte comes, its `.part` deleted, nothing recorded; one not yet begun isn't begun.
* **What a device keeps** is its own (`local`): items wanted by hand, which stay until deleted, and per series, a choice of episodes. A title or season wanted is its items as of then, each in the quality the player's picker shows, or if it lacks it, as players play it (the nearest lower, else higher); a version of parts is its parts; an item's key, that file alone. A series' choice is a count N ("download next": the latest in progress and the N unwatched after it, so the next is there before it ends, else the first N unwatched; specials left out) or `all` (specials too), kept however they're watched. An earlier `current` reads as the next 1.
* **Done with:** a series' download watched since it was fetched (its watched mark's clock past the fetch), unless wanted by hand or all of its series is chosen, is deleted as its space is needed, oldest fetched first. It goes only once another source holds it alike (its quality and size, not unavailable), as that source's server says too (a `HEAD`, as any member may write the record); the only copy, never. Reconciling also forgets copies whose files are gone (deleted by hand, or the folder changed), and never leaves less than 20 GB free.
* **Listings:** a crawl reads an `INDEX` if there is one, else JSON listings (Caddy's or nginx's), else HTML, reading only links' targets (decoded, checked, and encoded afresh, as other listings' names are). An `INDEX` has a path per line, as `find . -type f ! -name INDEX > INDEX` writes them, optionally followed by tab-separated size and modification time; a directory's ends in `/`, as Cinematheque's server lists them, so an empty one shows it's still there. A crawl takes no name with an empty, `.`, or `..` segment, a segment over 255 bytes, a path over 4 KiB, or a control character, nor over 4 million entries, so no source can write what other devices would refuse, or exhaust memory.
* **Crawls:** breadth-first with concurrent workers (16 by default), then bringing the source's copies in line with what was found. A crawl reuses a previous crawl's listing of any directory with only files whose modification time hasn't changed, except when asked for fully, which lists every directory afresh (a directory's time doesn't change as a file in it is rewritten in place, as retagging does). It follows up to 3 redirects, each within the source's origin; no other request follows one (a file's, a cover's, a sync's, pairing's), as it could lead anywhere. A crawl that fails anywhere changes nothing.
* **Unavailable:** a directory that held files and is still listed but holds none (an unplugged drive's mount point, or a NAS's) is one field on the source, `absent:<directory>` (relative to it, empty for the whole of it), noting when, its copies kept, rather than an operation per file; only the topmost of an unavailable subtree. A crawl clears it once the directory lists files again; once it's gone from its parent's listing (deleted, its copies going as deleted files' do); or a year on, as if deleted. A person may also remove its copies, as if deleted. Players show a title whose copies are all unavailable dimmed, and try unavailable copies last.
* **Time limits:** what waits on another host has a deadline ([deadline.zig](core/src/deadline.zig), as `Io`'s reads have none): a request's head to arrive, 30 seconds (a sync's sealed request too, and the rest of its body a mebibyte a minute); a listing, 2 minutes; an MP4's or a cover's range (the web client's too), 1 minute; whether another source holds a download alike (`HEAD`), 1 minute; a sync with one device, 10 minutes, of which its saying which device it is (`GET /sync`), answered at once, 10 seconds, and each response's head, built whole first, 2 minutes, so a device that takes connections and never answers (stopped in a debugger) holds up a sync with the others for seconds. A device serves 256 connections at most, 32 from one address (counted by a hash seeded afresh as it starts serving, so no one can choose addresses that crowd out another's). A download has a minute to answer, and a minute for each mebibyte after, so a large file goes on so long as bytes come.
* **Serving:** a device listens on the port given, else on 8008 or, if that's taken, any free port, and advertises the port it got. It binds with `SO_REUSEADDR` alone, never `SO_REUSEPORT`, so no two processes share a port. A connection that opens with a TLS handshake (a browser trying HTTPS first, as Safari does for an address typed) is closed at once, so the browser falls back to HTTP rather than waiting out the deadline for a request's head.
  * It answers `/sync`, and `/version`: JSON of what the build is (`version`, as [Version.xcconfig](apple/Version.xcconfig) sets it; `revision`, what it was built from, as `git describe --tags` gives it as each build runs, `-dirty` if a tracked file but [CHANGELOG.md](CHANGELOG.md) differed; `mode`, its optimizing; and `zig`), so a device's build can be told from afar, though it tells an attacker which known bugs it has (nothing of the machine, its paths, or its library).
  * It optionally serves media directories, each at its own path (the command-line app's one at `/media/`, the apps' by folder): files with single byte ranges, `If-Range`, and `mtime-size` ETags, nothing hidden (a name starting with `.`) served or listed; listings as JSON (Caddy's form, on `Accept: application/json`) or HTML; and, for the command-line app's, an `INDEX` with sizes, times, and directories, built at start and again on a request once it's a minute old, so drives plugged in or unplugged show. The apps' folders have no `INDEX`, as they change; each is opened afresh for each request, and one that isn't there (a share unmounted) lists empty at its root, so a crawl finds it unavailable rather than failing.
* **Discovery:** devices advertise `_cinematheque._tcp` by DNS-SD (Bonjour on Apple platforms, Avahi's compatibility library on Linux), named for the device's key (`cinematheque-` and its first 8 hex digits), so a person's devices are told apart. A device skips only itself: its name, that name as DNS-SD renames it for a second process sharing its data directory (as the Mac app and `serve` do), and any device that answers with its own key. The TXT record has the library's ID, the sync path, the person's key, and the device's and person's names, for showing devices by name, never for admitting anyone, as nothing in it is verified (people join only by code). At most 64 services are kept, resolved within 4 seconds in all, and found before the write lock is taken. A new device offering to be added advertises `pair` (`new`), the pairing path, and its name instead.

## Command-line app

* **Commands:** [usage.txt](cli/src/usage.txt) lists them, and is their help. Devices join only by code (`person pair` or `library join` offering, `person pair CODE` adding the device as this person's, `member pair CODE` as a new member's); an offer prints its code and the port it listens on, for a device that can't find it nearby (`pair CODE URL`). State commands are `NOUN VERB`, with verbs `list`, `show`, `add`, `set`, and `remove` where they apply, over nouns `person`, `library`, `member`, `device`, `source`, `title`, `alias`, and `progress`; whole-app actions are single words (`crawl`, `sync`, `serve`, `refresh`). Options are named (`--port`, `--leave`); `ls` and `show` are shortcuts for `title list` and `title show`.
* **Usage:** placeholders are in capitals, named for what they mean rather than their type (`URL`, `--port PORT`). `-h` or `--help` shows usage, of one noun or action if given, as does a noun alone; a command line that isn't one shows the same and exits with status 2. A command that fails says why in words on stderr (`error: this device has no library: create one (library create), or join one (library join)`), saying what to do where there's something to do, never with a trace, and exits with status 1. Its output shows control characters (but newlines and tabs) as `?`, as names come from files and other devices.
* **Downloads:** `title download` fetches a title's, a season's, or an item's files into a directory (the current one, or `--to`), as a device's downloads go (their paths, `.part` files, and only within the directory, since a crawling member's device chose the paths): in the quality given, else the one most of its items have; from its copies in copy racing's order, the next tried when one fails; a file already there at its size is kept, one of another size left alone.
* **Web client:** `serve` serves one at the root (plain HTML, CSS, and JavaScript, embedded in the app) unless `--no-web`. A browser acts as this device's person, so only one on this computer may (its request from a loopback address: `localhost`, or an SSH tunnel's end), any other told to open it there; `--permissive` lets every browser that reaches the port. Its details are in [cli/README.md](cli/README.md#the-web-client-in-detail).
  * **Setup:** a device with no library serves anyway, with syncing off until it has one, and the web client offers Create a Library, or Join a Library by a code, as the apps' setup does: offered at `/pair` on the same port and advertised as a new device, so a member's device adds it. Once it has a library, it names itself (by its computer's name) if it has no name, advertises itself as the library's, syncs, and keeps downloads if asked to. So `serve --media DIR` alone, with no other device, makes a working library.
  * **Settings:** the Mac's, on one page (`#settings`, at the sidebar's foot, and Home's links): names; people, removed, or someone new added by their device's code; this person's devices, renamed, removed, or added by code (those offering nearby, looked for again and again and listed as they're found, a row kept as its code's typed, one added after another until Done; or by the address one prints); sources, a server's address added, or the one folder `--media` serves (no other, so a browser can't share a folder of this computer's), removed, or an unavailable folder's videos removed; how often sources are looked through, and Refresh Library (or Fully), which syncs, then crawls every source but devices' downloads, taking the writer a source at a time; devices by address; and Leave This Library, as the apps leave (removing this device and syncing that first, a successor chosen if this person founded it and has no other device; with no one else in it, only forgetting), after which it's set up afresh. Setup's changes hold a lock taken before the writer, never after, and the device's library and identity another, held for nothing else, so any request may read them.
  * **Layouts:** two over the same pages, by the window's width (a CSS media query), not the device. Wide: the Mac's sidebar (the app's name and mark at its top, in the header's row and sharing its line, linking to the first page; then Movies, Series, Watching, Watched, and Kept; then a Lists heading with a ⊕ at its right, always shown, making a new list, then each of this person's lists, and other members' shared ones), search at the header's top right beside the shelf's name, and no Home. Narrow: the iPhone's tab bar at the bottom (Home, Movies, Series, Lists, and Search, search on its tab alone). Home is Watched and Kept as links, then Continue Watching and a row per list, each with See All (how many it holds) to its shelf; Lists is every list's row and New List.
  * **Addresses:** each page has its own (`#movies`, `#watching`, `#lists`, `#lists/<id>`, `#search`, `#settings`, a title's `#title/…`), so Back retraces them, and a title, a real link, opens in a new tab or is bookmarked. A title's page shows in the content, the sidebar marking the shelf it came from.
  * **Rows and grids:** rows (carousels) give every cover one height and each its own width by its shape (its placeholder's ThumbHash's, snapped to 2:3, square, 4:3, or 16:9, else a movie's 2:3 or a season's square; its cover's, once loaded), scrolling sideways. Grids give every cell the column's width, a season's cover of another shape fit whole in its square.
  * **Shelves:** otherwise the Mac's, with its grid, tiles, and status line. The Series shelf has Group by Series, a checkbox beside the order, kept in the browser: a tile per series as the Mac's, opening its seasons in place on a band below its row, in the grid's columns, its point under the series, which grows as the rows after it move down. Each list's page has Rename, Share, and Delete, confirmed first. A shelf's order is chosen beside search, each browser keeping its own. Each shelf keeps its place (where it was scrolled, and the series open) when shown again, as by Back from a title's page, or as its data changes: it's put back as it was left where it would show the same tiles in the same order, only those whose data changed drawn again, else built anew and scrolled back (a new search, order, or grouping starting at the top).
  * **Title pages and playing:** title pages as the apps', of what browsers play (MP4, M4V, or MOV, HEVC only where supported); playing as the apps do, full height with the browser's own controls, Back or Escape leaving.
  * **Keep:** with `serve --downloads DIR`, this device keeps downloads there as the Mac keeps its own (served at `/downloads/`, at its first hostname label `.local`, reconciled as a page changes them and every 10 minutes). Title pages choose them as Keep, as the Mac's inspector chooses Download (a movie's, a season's choice of episodes, each episode's, with sizes and the space available on the server, progress, and deleting, the only copy confirmed first), with a Kept shelf. It's refused if this device keeps them in another directory already (as the Mac app sharing its data directory does), as each would forget the other's files.
  * **Download** brings any item's file to the browser's computer through the server (from a copy racing chose, with its name, resuming by range, with no word of space, the browser's own business), as the browser may not reach the sources.
  * **API:** under `/api/`, the apps' JSON ([views.zig](core/src/views.zig)), with covers fetched by the server, since sources answer other sites' scripts nothing. Only URLs within the library's sources (of a source's origin, below its path, climbing out of it by no `..`) are fetched, raced, or noted as lost, a cover fetched with no redirect. It answers only by a host no other site can take (an IP address, `localhost`, a `.local` or single-label name, or the computer's own); its page opens from a link anywhere, but its API answers only its own page, changes as same-origin JSON; and nothing is to be framed or sniffed. A second after a browser's last change, it syncs with every device found or added, taking the writer for one at a time, so a page's writes wait out one exchange, not all. A file it relays that fails once begun drops the connection, short of its length, rather than answering again within it.
* **Added addresses:** addresses added are kept in `local`, on that device only; `sync` without a URL, and `refresh`, pull from every device discovered or added.

## Apple players

Their details, as built, are in [apple/README.md](apple/README.md#in-detail).

* **Structure:** one multiplatform app: a shared model, playback, title presentation, shelves, and setup, each platform's browser apart; one Xcode target, whose build phase links the core in as one object exporting only the C interface, so the compiler runtime Zig bundles can't clash with Xcode's; and, embedded on tvOS only, the Top Shelf extension.
* **Title presentation:** names as the core gives them; a season as "Season 3", or a dated series' by its year alone ("2026"), as "Season 2026" reads as a 2,026th; a quality picker by short names, the full name as help; the lists and watched marks quieter than what plays. Lists is a menu of every list, each checked if the title's on it, then New List…; its name is the same whatever it's on, its star filled if on any, so nothing beside it moves. The watched mark shows its state, toggled by pressing. Start Over, before Resume, is the one way to start over, as Mark as Unwatched forgets the position too.
* **Tiles,** on every platform: a cover's corners are spared, as a poster's title is often there; progress is a thin bar along its foot, white on a translucent track (as the web client's), so the art shows through. Under it, the title's name, wrapping to two lines where a row has room for it, its marks (downloaded, on the Mac; on a list; watched) at the line's end, so name and marks span the cover's width; a tile is as wide as its cover, so a long name never widens it or a row's gaps. Each mark is drawn one way everywhere, tiles and rows alike: downloaded, a blue arrow; on a list, a yellow star; watched, a green check. An item's row (a version, part, or episode; a season's, in the Mac's series inspector) has its marks at its line's end, before its runtime, and partway, a thin bar under its name; the Lists menu's star and the watched toggle's check, when on, are the same.
* **Shelves:** Home, Movies, Series, Lists, and Watched, in the core's orders (Watching, Watched, and Home's Continue Watching by when last watched, the latest first; the rest by title, until another's chosen), with search, counts (a series' shelf counting its episodes too), and empty text. A tile's context menu has Lists (as the title page's, a list chosen to put it on or take it off; not Add to List, which can't say taking off), and Mark as Watched and Mark as Unwatched (a season's; a whole series' on the Apple TV's series tiles, which have no Lists, as only movies and seasons go on lists). The Mac has Watching (what's in progress) in place of Home.
* **Setup:** Create a Library, or Join a Library, showing a code (a digit to a box, in two groups of three, as it's typed on the other device). On the Mac, it's in a welcome window as macOS apps' are (small and fixed, the app's icon and name over the two as large rows, the code shown in the same window, with Back); on the Apple TV, as tvOS's large choices. Neither app shows or takes keys.
* **Playing,** on every platform: fading in from black once the stream is ready (resuming 4 seconds before where it was left) as its sound rises, and out as it falls on leaving, the position saved there; saving every 10 seconds past the first 10 and where it's paused; marking an item watched at its end; going on to the next.
* **Copies:** a download on this Mac plays from its file, first. Else the chosen quality's available copies are raced (`cq_race`), so a server that's asleep costs a second or so, not a network timeout, and one that failed lately is tried last. When a copy doesn't load, the item's others follow: the quality's, then other qualities', the nearest at or below its resolution first, then the nearest above. An item lacking the chosen quality plays the first of those, which the Mac's inspector shows, dimmed, after its name, wrapping only whole ("Standard (720p Very Fast)").
* **Sharing:** while they run, the apps share the library (and the Mac its folders) on the port they got last; sync quietly a minute after they last did, whenever they come to the front, and a second after a change of their person's, pushing it to every device; and reload at once when a device pushes to them. Show sync activity shows the last exchange each way.
* **Reading back:** after a change (a person's, as a watched mark or progress saved; a sync's; a download's), the catalog is read back off the main thread, the latest read winning, as on a large library it takes a second; a tile marked watched or unwatched shows so at once. Only launching, pairing, leaving, and a refresh's end read it on the main thread.
* **Addresses from other devices:** only web addresses (http or https) are opened in the browser or fetched as covers (no more than the cover's length), and only paths within a folder are shown in Finder or played from it, as another member's device may have written them.
* **Settings' notes:** each says first why one would use the setting, then only what of how it works bears on choosing it (a NAS's disks waking, say); a confirmation says what an action does.
* **Retreat:** every flow has a way back out: a step's Back (or the platform's Back), a sheet's or dialog's Cancel, a download's Cancel; what can't be taken back is confirmed first, saying so.
* **Project:** Xcode's recommended settings but for script sandboxing (the core's build phase), the App Sandbox, the hardened runtime (until signing for distribution), and its macOS 15 minimum. Signing is in [Signing.xcconfig](apple/Signing.xcconfig), not the target, whose settings Xcode's Signing editor writes and which outrank it; a developer's own (the team) is in an ignored `Local.xcconfig` it includes, as it includes the version. [Info.plist](apple/Cinematheque/Info.plist) allows plain HTTP and Bonjour on the local network, and declares `cinematheque://` links on tvOS only, as the Mac handles none (SwiftUI would open a window for each).

Over the grid: the shelf's title; a shelf's own action (Downloaded's Show in Finder, its folder; Watched's Forget Watched…, every title on it unwatched, on all this person's devices, what's partway through untouched); and search, AppKit's field in the grid's toolbar, so it stays over what it searches (SwiftUI's search moved over the inspector while it was shown). The window is at least 960 points wide, so the grid's toolbar holds them with the sidebar and the inspector shown, as SwiftUI drops a toolbar item, not shrinks it, when it's short.
* **Inspector placement:** outside the split view, full height, attached only while shown (hidden, its collapsed divider took the window's edge, over the grid's scroll bar, and dragging the bar opened it). Its toggle is the app's, two of them, only one shown: after search while it's hidden, at the end of its own section while it's shown (the system's own came and went between launches).
* **Refreshing:** Refresh Library is in the File menu, ⌘R, and its ⌥ alternate, Refresh Library Fully, ⌘⌥R. At launch, with a library, the app shares it, syncs, names itself if need be, then crawls, syncing before writing anything, so a device whose replica was lost learns its own writes back first.
* **Status bar:** floating along the bottom of the grid, so fading moves nothing: the shelf's counts, or what went wrong; what's running, with progress, or the last exchanges if Show sync activity is on. It fades 3 seconds after it last changed, unless something is running or wrong, and comes back when the pointer nears it.
* **Tooltips:** short, sentence-style fragments without a period ("Delete download"), saying only what the control and the text around it don't: its name, for one that shows only a symbol; else a warning or state, as "The only copy". Explanations go in the pane's text.
* **Modelessness:** no alert nobody asked for, after the original Macintosh guidelines. An action is confirmed first only if it's hard to undo: removing a source (saying how many videos go, on every device, its files untouched), removing someone, leaving the library, forgetting what's watched, and deleting a download that's the only copy. Removing a device isn't, as it can join again as easily. What goes wrong shows in the status bar (and along the bottom of Settings) in words, never the core's error names, each source by its name, until dismissed, until the next action of its kind succeeds, or until the device gains or leaves a library.

## iPhone player (a prototype)

* **Data directory:** the app's Application Support, which iOS keeps.
* **Shelves:** a tab bar of Home (Continue Watching, then a row per list, each with See All, how many it holds, to the list's page; Settings from its corner), Movies, Series (a cover per series, in rows of one height, each cover its own shape, each full row scaled to fill the width, a justified layout, so a square cover beside portrait ones wastes no space; opening a page of its seasons, the series' whole name its heading, in square cells, each cover fit whole), Lists (every list's row, New List in the navigation bar; a list's page renaming, sharing, and deleting it from its menu, if it's this person's own), and Search. Rows are carousels, every cover one height, each its own width by its shape; grids give every cell the column's width.
* **Pages:** a movie's or a season's, its cover in its own shape, Play or Resume, Start Over (partway), the quality, the Lists menu and watched mark, then versions or episodes; a season's neighbors (‹ ›) in the navigation bar, moving in place.
* **Playing:** full screen, in AVKit's player, fading in from black as its sound rises, its close button lowering the curtain first.
* **Not yet:** setup is the Mac's welcome form, filling the screen; Settings only refreshes; nothing adds sources, pairs devices, or downloads.

## Apple TV player

* **Data directory:** in the caches, the only place tvOS lets an app keep files, which it may purge. Its seeds are kept in the Keychain too (this device's only, so no backup restored elsewhere acts as it) and put back at launch, so a purge loses only what syncing and crawling rebuild.
* **Refreshing:** at launch, naming itself (the Apple TV's name) if it has no name, sharing the library, syncing with devices found, then crawling the sources.
* **Exchanges:** with Show Sync Activity on, each exchange that changed something, in a corner for a few seconds.
* **Home:** a home page, no tab bar, one stack of pages from it, Back retracing them to it and from it leaving the app. At the top, the sections' buttons in a row (Movies, Series, Lists, Watched, then Search and Settings as symbols), focus starting on the first, as the system starts it; then Continue Watching, and a row per list under its heading, which is its link, "Favorites 3 ›" (how many titles it holds in grey), at the row's left edge, as Apple's apps' shelves', so a long row needn't be scrolled through, and moving up and down through headings lands on a row's first cover, not drifting right. Rows are carousels, every cover one height, each its own width by its shape (its cover's, else its placeholder's, else square).
* **Sections:** each a page: Movies, Series, Lists, Watched, Search, and Settings.
  * **Series:** a cover per series, opening a page of its seasons: its name, Play or Resume, named for the season to watch (the first not watched through), focused first, and the whole series' watched mark; then its seasons in square cells, each cover fit whole at its center, specials last. A series of one season opens it.
  * **Lists:** every list's row, as Home's, its heading the way to renaming and deleting. Its heading opens the whole list as a grid, its name heading the covers and scrolling with them, with Rename…, Share… or Stop Sharing, and Delete List… after them on a list of the person's own (naming on the full-screen keyboard at once, as Settings' names; deleting going back, as the page has nothing left to focus). New List is last, as these are rare.
  * **Grids:** under the section's name, a season everywhere but Series and Search, which show a cover per series, as the Mac shows seasons, so lists show just what they hold. Covers are six to a row, as tvOS's lockups (the cover lifting as it's focused, its name, as wide as its cover, moving out of its way), a series' (a season's) whole, in its own shape (square, 4:3, as its cover, else its placeholder, has it), at the foot of a movie's 2:3 box, so names line up along a row; a season's name under its series'.
* **Play/Pause on a tile** plays it at once, with no page between, as Apple's apps' tiles do: what its page's Play plays (a series' tile, the season to watch's), Back returning to the tile.
* **Settings:** as tvOS's Settings app's: the app's icon in the left half, the focused row's explanation under it, which VoiceOver reads as the row's hint; the list in the right, a grouped form, centered on the screen's height while it fits, its rows on plates of one height, their text inset as the system's, without symbols, under small uppercase headings; at accessibility text sizes, as the system's, values under their titles and the picture smaller. Its rows:
  * this Apple TV's name and its person's, each with a chevron, as the system's Name row, bringing up the full-screen keyboard as it's pressed (the system's Name page being private);
  * People, Your Devices, and Sources, each with its count and a chevron, opening a page of its own. People: the founder and you so marked, any other removed by pressing them, confirmed first, and Add Someone. Your devices: this one first, any other renamed or removed by pressing it (asked which), and Add a Device. Each adding page lists the new devices offering nearby, one pressed taking the code it shows on the full-screen keyboard's digits, a wrong one saying so, and once added, going back to the list, as Cancel does, always there to take focus (so Back works with no device found yet). Sources (but devices' downloads): each with its count of videos (the number alone), its path's middle folders collapsing into an ellipsis where it doesn't fit ("sulaco › … › TV Shows"), removed by pressing it, confirmed first, and Add Server, taking an address on the keyboard and looking for its videos (a Mac's folders, and where a source's quality comes from, stay on the Mac);
  * Refresh Library; Look for New Videos, opening a page of its choices, titled at the top, its row's chevron the system's; Show Sync Activity; and Leave This Library…, confirmed first, or, on the founder's only device, asking who takes over.
* **Top Shelf:** Continue Watching, then each list, as Home's rows (a dozen each), with covers (or, without one, its placeholder as the app draws it).
  * The app writes them, as they change, to its app group's container (`group.com.rbrian.cinematheque`, in its `Library/Caches`, the only place a device lets it write), which the extension reads. It writes at once, with the covers already on the Apple TV (else placeholders), then again as the rest are fetched, each kept as it comes, as fetching them all first, from sources whose disks may be asleep, outlasted the library's quiet spells, so nothing was written.
  * An item, selected, opens its title's page (`cinematheque://title?tile=…`), and with Play/Pause plays it at once (`&play=1`), as Apple's display and play actions do. The page is presented over the app, without a transition (one showed the app as it slid in), Back closing it to the page the app was on, as tvOS gives a screen it presents focus, its first, Play or Resume (pushed on Home within the tab view the app had, as the app came to the front, focus stayed in the tab bar, now and then). Playing, the page is beneath the player, to return to, black until it's left, so it isn't seen first (or shown at once, if it finds nothing to play).
* **Pages:** a movie's or a season's, over a blurred backdrop of its cover: its cover in its own shape, the series' name, and the season's, with the seasons before and after it as buttons in its top corner, beside the series' name ("‹ Season 6" and "Season 8 ›", the chevron alone, dimmed, at an end), moving to it in place, so Back still returns to where it was opened. Then Play or Resume, focused first (its details read before it's drawn, so it's there to be), Start Over, a Quality picker after Play (a title of one quality saying it as text), and the Lists menu and watched mark; then versions or episodes (described as a season's shown). The quality is the best it plays unless one's chosen: MP4, MOV, or M4V (not MKV or ISO), up to 2160p on a 4K display, else up to 1080p.
* **Playing:** full screen in the system's player. Until it shows, a spinner on the black (while the stream's made ready and the display switches, a few seconds, which black alone read as stuck): UIKit's large white one, at the screen's center, as the player's own, so they read as one. Its picture fades in only once the display has switched to the video's frame rate and range (if Match Content is on) and it's playing, its sound rising. The remote and info panel work as the system player's.
* **Leaving:** Back fades it out as its sound falls, gives the display its own mode back behind black, then fades the page back in. Going to the background, it pauses, silent, and comes back paused.

## Debugging

* The apps log to the system's log (Xcode's console), under `com.rbrian.cinematheque`, a line where it helps tell what's slow: each start of playback, its steps' times (`playback`); each Top Shelf written (`topshelf`, how many rows of how many titles, or why not); and each crawl, the sources crawled (listing, listings read and reused, and recording) or failed, and describing's after (`crawl`), from `cq_crawl`'s results, those skipped as crawled lately unsaid. What was logged to find problems since fixed is gone.
* Debug builds take launch options for driving the app unattended (in a VM by `open --env`; in the tvOS and iOS simulators by `simctl launch`, each prefixed `SIMCTL_CHILD_`):
  * `CINEMATHEQUE_DATA` (iOS and tvOS; the Mac's core reads it in any build): a data directory to run on, as a simulator's on one of the Mac's (a copy, as it's written to), its own left alone, and on tvOS, its Keychain's seeds neither read nor written.
  * `CINEMATHEQUE_CODE_FILE`: a file each pairing code offered is written to, for a test to send from another device.
  * `CINEMATHEQUE_SELECT`: a tile (e.g., `t/s/firefly/-#1`), selected on macOS, its page opened on tvOS and iOS; or a series' seasons, by its key.
  * `CINEMATHEQUE_TAB`: on iOS, a tab (`home`, `movies`, `series`, `lists`, or `search`); on tvOS, a section's page (`movies`, `series`, `lists`, `watched`, `search`, or `settings`), opened from Home; on both, in setup, a step, `join`, offering its code.
  * `CINEMATHEQUE_DOWNLOAD_FLOOR`: the free space downloads keep, in bytes, for a VM's small disk; any build, read by the core.
  * `CINEMATHEQUE_LEAVE` (tvOS, on Settings, once a launch): `ask` presses Leave This Library…, `confirm` confirms it too, the first other member taking over if asked.
  * `CINEMATHEQUE_PAGE` (tvOS, once a launch): on Settings, a page (`people`, `devices`, `sources`, or the page for adding, `add-someone` or `add-device`); on the Lists page, a list's (`list:<id>`).
  * `CINEMATHEQUE_PAIR` (tvOS, once a launch, on a page for adding): a code to enter for the first new device found.
  * `CINEMATHEQUE_SERVER` (tvOS, once a launch, on Sources): an address to add.
  * `CINEMATHEQUE_APPEARANCE`: `dark` or `light`, the app's whatever the system's (the tvOS simulator's can't be set).
  * `CINEMATHEQUE_PLAY` (once a launch): a URL to play on macOS, with `CINEMATHEQUE_ITEM`, its item key, for its progress; any value on tvOS and iOS, to play the opened title.

## Implementation

* Zig 0.17+ for the core and the command-line app, with no dependencies beyond the system's SQLite and DNS-SD. Whatever waits (networking, sleeping, SQLite waiting out another connection's write, DNS-SD waiting for results) does so through Zig's `Io`, so it can be canceled; only what `Io` can't reach blocks outside it (SQLite's own disk I/O, and the system's name lookup, which copy racing avoids on Apple platforms by looking names up through DNS-SD).
* Releases of the core and the command-line app are built ReleaseSafe, never ReleaseFast: they parse what sources and other devices send, so a bug must stop them, not corrupt memory.
* **Versions:** one, `MARKETING_VERSION` in [apple/Version.xcconfig](apple/Version.xcconfig), from 0.1: the Apple app's (by [Signing.xcconfig](apple/Signing.xcconfig), the project setting none), and the command-line app's (read by its `build.zig`). The core depends on nothing of `apple/`: whoever builds it gives its version (`-Dversion`, the Apple app's build phase its own). A release is a tag `v` and it; its commit renames [CHANGELOG.md](CHANGELOG.md)'s Unreleased to the version.
* **CI** ([.github/workflows](.github/workflows)): on every push and pull request but those changing only documentation (Markdown, `docs/`, the license), the core's tests, the command-line app ReleaseSafe and [cli/test.sh](cli/test.sh) on Linux and macOS (allowed to fail on macOS, whose Local Network privacy may keep the runner's processes off the LAN), and the Apple app for macOS and the tvOS and iOS simulators. On a tag `v*`, once it matches the version, a GitHub release, its notes the version's changelog section ([tools/release-notes.sh](tools/release-notes.sh)): the command-line app for macOS and Linux, each on aarch64 and x86_64, as `.tar.gz` with SHA-256 checksums, and the Mac app, Release, signed ad hoc, zipped.
* SwiftUI for Apple players.
* SQLite for each device's replica.
* Tests: the core's unit tests (`zig build test`; `zig build` compiles the C interface too), [cli/test.sh](cli/test.sh) (two devices and more, end to end), screenshots of the macOS player in a macOS VM (terrarium's `macos-27.2-quiet`), and of the Apple TV player in the tvOS simulator (an Apple TV 4K, 3rd generation); the README's, of every player on the mock library, by [tools/screenshots.sh](tools/screenshots.sh).

## Scale

100,000+ video files: 4,000+ movies, and 500+ TV series of up to 30 seasons of up to 50 episodes.

## Risks

* App Review may resist publishing a library that encroaches on Apple's own, all the more so one that serves media.
* Outside metadata comes from providers outside Cinematheque, whose sources' terms (e.g., TMDB's charge for commercial use, IMDb's datasets for personal use only) bind them, not Cinematheque.
* GPL tools (`HandBrakeCLI`, GPL builds of FFmpeg) must run as separate processes, never linked, or they bind the license of the players and the shared core.
